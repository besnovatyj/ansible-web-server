# Заметки Claude по Ansible-проекту

Решения, запреты и грабли, накопленные при работе с этим проектом. Сверено с кодом 2026-09-27.
Формат пункта: **правило** → почему → где в коде.

Проект универсальный, под конкретный сайт не затачивается. Домены, имена пользователей и прочие значения берутся из inventory.

---

## 1. Общие принципы

**Серверы живут без присмотра («настроил и забыл» на 3–5 лет).** Мониторинга, который кто-то читает, нет, но при проблемах звонят владельцу. Поэтому:
- автообновления безопасности включены: непропатченная дыра опаснее, чем поломка от патча на LTS;
- авто-ребут ночью обязателен, иначе обновления ядра и glibc не вступают в силу;
- никаких решений, которые требуют регулярно читать почту, дашборды или что-то делать руками;
- секреты и конфиги хранятся в файлах, чтобы переживать перезагрузку;
- заранее закрыты главные «тихие» отказы: переполненный `/boot` и битый `apt.conf.d`, которые ломают apt.
- Где в коде: роль `system/unattended_upgrades` (плейбук `50-server-security`), обоснование — п.15 `TODO/000-NOTES.MD`.

**Как работаем с замечаниями.** Владелец даёт замечания по одному. По каждому я сначала разбираю, подходит ли совет под модель «без присмотра» (generic-советы можно и нужно оспаривать), и только потом правлю.
- Решения «не делаем, потому что…» записываются в `TODO/000-NOTES.MD`.
- Исправленные пункты аудита отмечаются в `TODO/000-AUDIT.md`. Там сделаны B1, B2, M5. H1–H4 и M1–M4, M6–M8 **намеренно отложены**, без запроса их не трогать.

**Встроенные модули вместо shell.** Первый выбор — модуль (`copy`, `template`, `file`, `lineinfile`, `command`), `shell` — в последнюю очередь. Если встроенная возможность требует неудобного контракта (например, `validate` с `%s`), лучше не использовать её и проверить отдельным следующим таском. Прежде чем писать новое, посмотреть, нет ли в этой роли таска, который уже делает то же самое.

**Syntax-check запускает владелец** (ansible стоит у него на хосте, у Claude его нет):
`ansible-playbook --syntax-check playbooks/<плейбук>.yml -i inventory/hosts.yml`, или весь набор через цель в Makefile.

## 2. Плейбуки и make

**Нумерация десятками**, между номерами остаётся место для вставки:

| Плейбук | Что делает |
|---|---|
| `10-local-init` | локально: SSH-ключи и known_hosts |
| `20-bootstrap-access` | пользователи и ключи; единственный заход по паролю root |
| `30-server-base` | apt, локали, swap, systemd |
| `40-server-access` | journald для SSH, проверка входов |
| `50-server-security` | UFW, hardening sshd, автообновления, fail2ban |
| `60-webserver` | nginx, php, mysql, redis и т.д. |
| `70-release` / `70-release-db` | выкладка приложения (с импортом БД или без) |
| `80-certbot` (+ `-staging`, `-force`) | сертификаты |
| `90-queue` | воркеры очередей |
| `verify` | повторяемая проверка сервера, запускается когда угодно |
| `optional-*` | резерв: не входят в общие цели и в syntax-check |

- make-цель = имя плейбука без `.yml`.
- `make provision` = 10…60 + verify (чистый сервер целиком).
- `make deploy` = 70 → 80 → 90 + verify (первая выкладка; дальше обычно по шагам).

**Хвосты переименования:**
- в readme и `TODO/` ещё встречаются старые имена `stage-N`: владелец отложил их обновление на конец. Соответствие: stage-0 → 10, stage-1b → 20, stage-1 → 30, stage-2 → 40, stage-3 → 50, stage-4 → 60, stage-5d → 70, stage-5a → 80, stage-5b → 90, stage-6 → verify, stage-5c → optional-data-transfer, full-deploy → provision;
- роли `users_provision` и `ssh_push_keys` в комментариях ссылаются на несуществующий `000-ANALYSIS.md`, видимо, имелся в виду `TODO/000-AUDIT.md`.

## 3. Проверки после плейбука (Post-checks)

**Правило:** в конце плейбука стоит отдельный плей «Post-checks», который проверяет результат.

| Плейбук | Что проверяется |
|---|---|
| 10 | все ключи на месте, права 0600 (приватный) и 0644 (публичный) |
| 30 | swap включён, локали (см. §5), часовой пояс |
| 50 | UFW активен, jail sshd работает, входы по ключам, политика sshd (строго) |
| 60 | сервисы запущены, сокет PHP-FPM есть, порт 80 открыт; в CLI доступны `proc_open` и `allow_url_fopen` |
| 70 | свои проверки релиза |
| 80 | сертификат есть, `nginx -t` проходит после certbot (certbot правит конфиг) |
| verify | **строго:** сервисы, SSH, UFW, fail2ban, нужные php-модули (OPcache, apcu, redis, pdo_mysql, mbstring, intl). **Только отчёт:** HTTP/HTTPS — намеренно, до certbot HTTPS нет |

Порт 443 в `60` не проверяется: HTTPS появляется только после `80-certbot`.

## 4. SSH: ключи, агент, sshd

### Ключи
- **Passphrase есть у всех ключей**, включая automation-пользователя ansible. Passphrase хранятся в vault (`vault_user_<имя>_passphrase`), копии ключей — в KeePass. Пустая passphrase запрещена политикой (`ssh_generate_local_keys`).
- **Ключи лежат в `~/.ssh/<домен>`** (`local_ssh_keys_dir` в `inventory/group_vars/all/ssh.yml`), то есть на родной ФС Linux (ext4).
  - Почему: раньше они лежали рядом с плейбуком на примонтированном Windows-диске. Там все файлы получают права 0777, `chattr` не работает, и ssh отказывается от таких ключей.
  - **Не возвращать** обходные трюки той поры: пустышки ключей, `regenerate: full_idempotence`, пробу `.perm_probe`.
  - Бэкап ключей из `~/.ssh` — отдельный ручной шаг (KeePass).
- **`type` в `server_users`** описывает UNIX-аккаунт, а не ключ:
  - `automation` — пароль заблокирован, sudo без пароля;
  - `human` — пароль в `/etc/shadow`, sudo с паролем.

### Агент (`make agent-up`)
- Агент поднимается один раз за сессию и один раз спрашивает passphrase ключей. Адрес сокета сохраняется в файл `.agent.env` (не в git), цели читают его через обёртку `$(PLAY)`.
  - Почему через файл: make запускает каждую строку рецепта в новом shell, и `export` не доживает до следующей цели.
- `agent-up` можно запускать повторно: он проверяет, жив ли агент, и добавляет только недостающие ключи.
- Цели 20…90 и verify зависят от `agent-up`. Цель `10` агента не требует: ключей на этом этапе ещё нет.
- **Раскладка make-конфига:**
  - `.env` — настройки проекта (домен), формат `KEY=value` без кавычек. Домен дублирует `domain_name` из inventory: make не читает yaml, синхронизировать руками;
  - `environments.mk` — переменные make (`SSH_KEYS_DIR`, `AGENT_ENV`, `AGENT_KEYS`, `PLAY`);
  - `Makefile` — только рецепты;
  - `scripts/agent-{up,down,status}.sh` — сама логика агента.
- **Добавить пользователя:** запись в `server_users` с `key_passphrase_vault_key`, passphrase в vault, путь ключа в `AGENT_KEYS` (`environments.mk`). Списки обязательных ключей в плейбуках 40, 50 и verify собираются автоматически.

### Подключение
- **`IdentitiesOnly=yes` задан глобально** в `ansible.cfg` → `ssh_args`. В ролях, которые сами вызывают `ssh -i …`, его тоже ставить.
  - Почему: без него ssh сначала перебирает все ключи агента и может упереться в серверный лимит попыток (`MaxAuthTries`) раньше, чем дойдёт до нужного.
  - `IdentityAgent=none` не использовать: агент — часть схемы.
- **Мультиплексирование SSH выключено** (`ControlMaster=no`, `ControlPath=none`), скорость компенсирует `pipelining = True`. **Не включать обратно.**
  - Почему: баг Ansible #79992. После перезагрузки сервера модуль `reboot` бесконечно стучится через мёртвое мультиплексированное соединение и «висит» минутами, хотя сервер поднялся за 6–11 секунд. Уменьшение ControlPersist не помогает. Это не медленный VPS.
  - Если reboot всё же завис: сервер уже перезагрузился, флаг `/var/run/reboot-required` исчез, и при повторном запуске таск пропустится.
  - Оставлены `meta: reset_connection` после ребута (безвредная страховка), `reboot_timeout: 900` и `post_reboot_delay: 15`. Это потолок ожидания, а не фиксированная пауза.
- **Ключ automation-пользователя ограничен опцией `restrict,pty`**, а не просто `restrict` (`roles/system/ssh_push_keys`). **Не убирать `pty`.**
  - Почему: `reboot` выполняется через sudo, и Ansible требует для него терминал (pty). Чистый `restrict` запрещает pty, и reboot падает с `PTY allocation request failed`. Остальные запреты (агент, X11, проброс портов) продолжают действовать. Защиты `no-pty` почти не давал: exec и sftp он всё равно не блокирует.
  - Со стороны sshd pty нигде не запрещён (`PermitTTY` не задаётся).
  - После смены опции нужно заново раздать ключи (`20-bootstrap-access`, повторный запуск безопасен).
  - Ключам людей `restrict` не ставится: им нужен интерактивный терминал.
- **`delegate_to: localhost` наследует `become`.** Если плей запущен с `become: true`, то таск, делегированный на localhost, попытается выполнить sudo на ЛОКАЛЬНОЙ машине и упадёт с `sudo: a password is required`.
  - Правило: у каждого таска с `delegate_to: localhost` или `connection: local` явно ставить `become: false`.
  - Сейчас так сделано в `verify_ssh`, `ssh_agent_check`, `release`, `data_transfer`.

### sshd
- **Политика после hardening:** root входит только по ключу (`PermitRootLogin prohibit-password`), вход по паролю запрещён всем (`PasswordAuthentication no`, `KbdInteractiveAuthentication no`).
- **Hardening делается только своим drop-in файлом** `/etc/ssh/sshd_config.d/00-hardening.conf`, а `50-cloud-init.conf` удаляется (роль `ssh_remote_security`). **Не возвращать** правку основного `sshd_config` через `lineinfile`.
  - Почему: в sshd побеждает ПЕРВАЯ встреченная настройка, а файлы из `sshd_config.d/` читаются раньше основного конфига. Файл cloud-init с `PasswordAuthentication yes` перебивал правки основного конфига.
  - cloud-init на уже установленной машине свой файл повторно не создаёт.
  - Новые SSH-настройки добавлять в этот же drop-in.
  - Проверка конфига — `sshd -t` без `-f`: с `-f <drop-in>` sshd ругается на отсутствие HostKey.
  - `sshd -T` показывает итоговые значения после слияния всех файлов, поэтому проверки по нему надёжны.
- **Роли проверки доступа:**
  - `ssh_agent_check` — перед плеем: агент запущен и нужные ключи в нём есть, иначе «запустите make agent-up»;
  - `verify_ssh` — реальный вход по ssh;
  - `verify_sshd_policy` — сверка настроек `sshd -T` без shell-скриптов. До hardening допускает `PermitRootLogin yes`, после (50 и verify) — строго `prohibit-password`.
- **Диагностика.** Сообщение `Server accepts key` → `No more authentication methods to try` при запуске без агента означает, что ключ с passphrase нечем разблокировать. sshd тут ни при чём.

## 5. Роли: решения и грабли

### apt (`roles/system/apt_update`)
- **`force_apt_get: true` обязателен.** Без него модуль идёт через python-apt, который на слабом процессоре минутами перестраивает кэш пакетов, и роль «висит». Через apt-get то же самое занимает ~20 секунд.
- **Не предлагать `flock`** для ожидания блокировки dpkg: на Linux он не видит блокировку, которую ставит apt. Ждать блокировку умеет сам модуль apt: `lock_timeout`.
- **Не предлагать `default_release: <релиз>-security`**: это приводит к ошибке `value 'noble-security' is invalid`. Security — это не отдельный релиз. Если понадобятся только security-обновления, их задают через привязку к источнику (origin), а не через `default_release`.
- Роль можно перезапускать на «грязном» сервере: перед обновлением выполняется `dpkg --configure -a`.
- У каждого долгого apt-таска есть `async`-лимит: при зависании роль падает, а не ждёт вечно.

### Локали (`roles/system/locales_hostname_timezone`)
- Приложения русские, консоль сервера английская. Язык приложения от системной локали не зависит (PHP intl/ICU, collation MySQL).
- Генерируются обе локали, системная — `en_US.UTF-8`. `ru_RU.UTF-8` только сгенерирована, на случай если приложение явно её запросит. Русский LANG и LC_TIME на ОС не ставить.
- **`community.general.locale_gen` на Ubuntu 24.04 не работает**: сообщает об успехе, а локалей нет. Вместо модуля используется команда `locale-gen <локали>` с предварительной проверкой `locale -a`. **Не возвращать модуль**, даже ради «правильного» стиля. Пакет `language-pack-ru-base` не нужен.

### PHP (`roles/web-server/php`)
- **Hardening (`security.ini`: запрет опасных функций, `allow_url_fopen=Off`) — только для php-fpm, не для CLI.**
  - Почему: composer, консольные команды и воркеры очередей легитимно используют `proc_open` и скачивание по URL. Однажды с hardening в CLI упал composer install при релизе.
  - Роль удаляет `security.ini` из CLI, если его туда положила старая версия. Регрессию ловит проверка в `60`.
  - Не предлагать «захарденить CLI как FPM». Для нового ini-файла решать, нужен ли он обоим режимам.

### fail2ban (`roles/system/fail2ban`)
- Фильтры для входов в приложение (`yii2-auth`, из journald) и Redis разложены заранее, но их jail'ы **намеренно выключены**: до выкладки приложения логов нет, и fail2ban упал бы с «лог не найден». Владелец включает их сам после деплоя переключателями `jails_enable_status` в `group_vars/all/security.yml`.
- Если после прогона активен только sshd — это норма, а не недоделка. Фильтры не удалять. Уместно напомнить о них в чеклисте после деплоя.

### Ограничение частоты запросов (rate limiting)
- **Не внедряем** (`limit_req` в nginx). Не предлагать без явного запроса.
  - Почему: реальной нагрузки никто не измерял, атак не было. Админка шлёт много мелких запросов (HTMX/AJAX), реалистичный порог — около сотни в секунду. Пробные лимиты в dev приводили к блокировке самого себя.
  - Цифры из dev (Traefik) в nginx переносить нельзя: при тех же числах nginx режет жёстче.
  - jail `nginx-limit-req` объявлен, но выключен (`nginx_limit_req: false`) — это норма.
- Если когда-нибудь вернёмся: сначала замерить реальную нагрузку, жёсткий лимит ставить только на страницу входа в админку, статику не трогать.

### nginx: виртуальные хосты (`roles/web-server/nginx`, 2026-10-19)
- **Шаблон — по механизму nginx, а не по сайту:** `vhost-php.conf.j2` (файлы + фронт-контроллер PHP) и `vhost-static.conf.j2` (только файлы). Всё, чем различаются фронт, админка, статика и будущий REST (лимиты, таймауты, заголовки, CSP, CORS), — данные `nginx_sites` в `inventory/group_vars/all/nginx_sites.yml`; умолчания — `nginx_site_defaults` роли.
  - Почему: роль не должна знать ни имён поддоменов (`files` однажды переименуют), ни частей приложения, ни их политик. **Не заводить шаблоны по назначению сайта** (`frontend.conf.j2`, `rest.conf.j2`) — этот вариант владелец отверг как нелогичный.
- Файл на сайт: `/etc/nginx/sites-available/<domain_name>-<name>.conf`; лишние файлы с префиксом домена (в т.ч. прежний общий `<domain_name>.conf`) роль удаляет. Сервер по умолчанию `00-default.conf` (444 и `ssl_reject_handshake`), ссылка на стандартный `default` Ubuntu снимается.
- **`add_header` только с `always` и только на уровне server.** Заголовки server наследуются в location, лишь если там нет своего `add_header`; старый конфиг так терял заголовки безопасности на статике (`add_header Cache-Control` в location). Кэш — через `expires`.
- Задачи vhost — в `tasks/sites.yml`, их вызывает и 80-certbot (`include_role … tasks_from: sites`).

### TLS и certbot (`roles/web-server/certbot`, 2026-10-19)
- **`certbot certonly --webroot`, не `--nginx`.** Конфиг nginx certbot не трогает; 443, редирект и HSTS рисует шаблон, когда есть `fullchain.pem`. Токены — в `acme_webroot` вне корня релиза. `--deploy-hook "systemctl reload nginx"` пишется в настройки продления.
  - Почему: `--nginx` правил тот же файл, который перезаписывает 60 (повторный прогон снимал HTTPS), и подключал свой `options-ssl-nginx.conf` — он годами «стареет» вне git. На старых серверах это дало TLS 1.0/1.1 и шифры без FS, и устройства Apple не открывали сайт (`/workspace/TODO/Certbot/Certbot.md`). **Не возвращать `--nginx` и `options-ssl-nginx.conf`.**
  - Сертификат, выпущенный прежней схемой (`installer = nginx` в renewal-конфиге), роль не переводит сама — останавливается с инструкцией (команда `certbot reconfigure` на сервере не проверялась).
- Настройки TLS — одни, в `nginx.conf.j2` (http): Mozilla Intermediate без DHE, `ssl_prefer_server_ciphers off`, тикеты выключены. OCSP stapling не включать: Let's Encrypt прекратил OCSP в 2025.
- **HTTP/2 зависит от версии nginx:** до 1.25.1 — параметр `listen 443 ssl http2`, с 1.25.1 — `http2 on`. Версию роль берёт с сервера (`nginx -v`), шаблон выбирает форму сам.
- **IPv6:** vhost слушают `[::]`, если у сервера есть IPv6 (факты). Pre-flight 80 проверяет AAAA: запись не на этот сервер = тихий отказ на телефонах в мобильной сети и при проверке Let's Encrypt.
- Post-checks 80 повторяют `/workspace/TODO/Certbot/check_certbot_tls.sh` с самого сервера: TLS 1.0/1.1 — по `nginx -T` (OpenSSL 3 на сервере сам не умеет TLS 1.0, неудачное рукопожатие ничего не доказывает), TLS 1.2 + FS + fullchain + цепочка, TLS 1.3, ALPN h2 — по каждому домену.

### MySQL (`roles/web-server/mysql`)
- **Версия 8.4 LTS**, одна и та же в разработке и на сервере. Ставится из репозитория Oracle (`mysql-8.4-lts`): в Ubuntu 24.04 есть только 8.0. Пароль root задаётся через debconf.
- **Аутентификация только `caching_sha2_password`.** `mysql_native_password` в 8.4 удалён, его упоминание ломает запуск. По той же причине удаляется несовместимый `python3-mysqldb`.
- Логи идут в syslog/journald, отдельных файловых логов не заводим.
- Конфиги сервера и dev-окружения раздельные, общий базовый конфиг не делаем.
