# Анализ Ansible-проекта `/workspace/ansible`

Дата: 2026-07-19.
Охват: все плейбуки, Makefile/environments.mk/.env, ansible.cfg, inventory + group_vars,
структура ролей и их подключение, документация (readme*, TODO/000-*).
**Вне охвата (по договорённости):** содержимое `optional-docker.yml` и `stage-5c-data-transfer.yml` 
— для них проверено только то, что они полноценно подключены в проект (см. §7).

---

## 1. Общая оценка

Ядро проекта в хорошем состоянии: стадии реальны и работоспособны, у каждой есть
pre-flight и post-check'и, bootstrap идемпотентен, секреты изолированы в vault,
осознанные решения (отключение SSH-мультиплексинга, ssh-agent, fire-and-forget-политика)
задокументированы прямо в коде. Неиспользуемых ролей нет, «висящих» плейбуков нет.

Проблемы проекта — почти целиком **навигационные**, и они подтверждают ощущение
«разбросано и запутано»:

1. **Имена стадий врут о порядке запуска** — `stage-1b` идёт *до* `stage-1`;
   буквы `5a/5b/5c/5d` не соответствуют фактическому порядку (`5d → 5a → 5b`);
   `stage-6` в `full-deploy` выполняется *до* любых пятых стадий.
2. **Канонический порядок запуска нигде не записан целиком.** `readme.md` устарел
   (не знает про `make release`), актуальный порядок лежит в рабочих заметках
   `readme-TODO 2.md` — файле, который по имени выглядит черновиком.
3. **Конфигурация размазана по 8 файлам** с четырьмя точками ручной синхронизации
   (см. §5) — каждая из них честно задокументирована по месту, но сводной карты
   «что и где править» не было.

Ни одна из находок не блокирует деплой. Дальше — детали и рекомендации.

```
stage-4    site       Redis, Memcached, MySQL, Nginx, PHP,      + composer, app_secrets,
                      apt_clean                                  service_restart
stage-6    site       комплексная верификация (гибрид            HTTP/HTTPS probe не валит прогон —
                      enforcing/report)                          HTTPS до 5a законно отсутствует
```

### Ручная пост-деплойная часть (канонический порядок)

```
make release     stage-5d  git clone + composer install + php init (+ release-db: импорт дампа)
make stage-5a    stage-5a  certbot (требование: DNS уже указывает на сервер)
```

Зависимости, зафиксированные в самих плейбуках: `5d` требует stage-4
(php-fpm + composer, проверяется pre-flight'ом); `5a` требует stage-4 + DNS;
`5b` требует задеплоенных исходников. `5a` и `5d` между собой не упорядочены
жёстко (nginx-роль stage-4 создаёт скелет web-корней, так что certbot пройдёт и до
релиза), но канон из заметок — `release → 5a → 5b`.

### Резерв (подключено, не запускается)

```

make docker-install  optional-docker         (установка Docker)
```

## 3. Путаница в именовании — разбор по пунктам

### 3.1. `stage-1b` выполняется до `stage-1`

Суффикс «b» читается как «после 1», а фактический порядок — `0 → 1b → 1 → 2`.
Это прямо признано в шапке `stage-1-server-base.yml` («Порядок: stage-0 →
stage-1b (bootstrap) → ЭТОТ stage-1»), т.е. имя приходится опровергать комментарием —
верный признак, что имя неудачное.

**Варианты** (по возрастанию стоимости):

- Оставить, но в `make help` и readme всегда писать порядок явно (сейчас так и есть —
  работает, но каждый новый читатель спотыкается).
- Переименовать в `stage-0b-bootstrap-keys` — «мост» между локальной подготовкой и
  настройкой ОС; правки: имя файла + 2 строки Makefile + упоминания в readme и
  шапках stage-0/stage-1. Семантически честно и дёшево. **Рекомендую этот вариант.**
- Полная перенумерация (bootstrap = stage-1, ОС = stage-2, …) — дорого: сдвигаются все
  номера, комментарии, память, документация. Не стоит того.

### 3.2. Буквы `5a…5d` не соответствуют порядку запуска

Фактический порядок: `5d (release) → 5a (certbot) → 5b (queue)`, `5c` — резерв.
Буквы отражают историю появления плейбуков, а не последовательность. Дополнительно
`5d` — единственная стадия, чья make-цель (`release`) не совпадает с именем файла
(`stage-5d-release.yml`), плюс у неё есть вариант `release-db`.

**Рекомендация — не переименовывать файлы, а сменить трактовку и закрепить её:**
группа `5x` — это не последовательность, а *набор независимых пост-деплойных операций*,
каждая со своими предусловиями. Тогда буквы — просто идентификаторы. Чтобы порядок
не приходилось помнить:

```make
# Пост-деплойная фаза одним заходом (порядок каноничен: код → TLS → очереди → проверка)
post-deploy: release stage-5a stage-5b stage-6
```

Одна комбинированная цель снимает 90 % путаницы: `full-deploy` + `post-deploy` — и весь
порядок закодирован в Makefile, а не в памяти. (Если всё же захочется переименовать —
честная схема: `5a-release`, `5b-certbot`, `5c-queue`, `5d-data-transfer(reserve)`;
но это ломает привычку и историю логов, выгода сомнительна.)

Имя цели `release` вместо `stage-5d` — скорее фича (человекочитаемо), но стоит добавить
alias, чтобы `make stage-5d` тоже работал — тогда ряд `stage-*` полный:

```make
stage-5d: release
```

### 3.3. `stage-6` запускается раньше пятых стадий (и дважды)

`full-deploy = … stage-4 → stage-6`, затем stage-6 рекомендуется повторно после `5b`.
Номер «6» обещает «после 5», по факту это повторяемая проверка, а не этап. Плейбук
к этому готов (HTTP/HTTPS probe намеренно не валит прогон до certbot) — т.е. семантика
уже «verify, запускаемый когда угодно», и только имя говорит иное.

**Рекомендация:** минимально — ничего не менять, это работает. Идеологически чище —
переименовать в `verify.yml` / `make verify` без номера, подчеркнув повторяемость.
Средняя цена (файл + Makefile + readme), выгода — исчезает последний «врущий» номер.

  в stage-3. Стоит добавить строку статуса в шапку `roles/system/app_armor/tasks/main.yml`

- **fail2ban-фильтры `redis-auth`/`yii2-auth` разложены заранее, jail'ы выключены** в
  `security.yml` — намеренно (включаются после первой выкладки / после Monolog→Syslog).

  `roles_path = ./roles/`, но все плейбуки пишут относительные `../roles/system/...`.

  короткие имена (`- system/ufw` — roles_path это позволяет, запуск из корня проекта
  гарантирован обёрткой `$(PLAY)`), либо убрать roles_path из cfg как неиспользуемый.
  Мелочь, но именно из таких мелочей складывается «как-то всё разбросано».

## 8. Прочие находки по плейбукам и обвязке

Мелочи, найденные попутно (роли глубоко не аудировались — это уже сделано в
`TODO/000-AUDIT.md`, его статусы актуальны):

1. **Устаревший комментарий в `stage-0-local-init.yml:7`** — «Генерация SSH-ключей …
   в `secrets/ssh/`». Ключи давно переехали в `~/.ssh/<домен>/` (`local_ssh_keys_dir`,
   миграция из-за drvfs/прав). Комментарий врёт о ключевом пути.
2. **`stage-5b` не проверяет своё главное предусловие.** Шапка роли queue заявляет:
   «должны существовать `{{ web_root }}/{{ domain_name }}/yii` и рабочий .env», но
   pre-flight'а на это нет (assert на `queue_workers_count` есть — M5 закрыт, а H1 из
   аудита в части 5b остался). Воркеры поднимутся и начнут циклично падать/рестартовать.
   Дешёвый фикс: `stat` на `yii` + assert перед установкой юнита. Заодно: упоминание
   «рабочий .env» в шапке устарело — приложение читает `/run/secrets` (app_secrets),
   а не .env.
3. **DNS-pre-flight `stage-5a` проверяет только `domain_name`**, а certbot выпускает
   сертификаты для всех `server_name` из `nginx_sites` (включая `www.`, `adm.`,
   `files.`). Если поддомены в DNS не заведены, pre-flight пройдёт, а certbot упадёт
   позже с менее понятной ошибкой. Дополнительно `dig +short` при CNAME вернёт
   несколько строк и сравнение с `host_ip` даст ложный отказ. Улучшение: цикл по всем
   хостам из `app_hosts` (+www) и сравнение `in stdout_lines`.
4. **`full-deploy` заканчивается на stage-6, пост-деплойной комбинированной цели нет** —

5. **Бэкап-файлы рядом с боевыми**: `roles/web-server/certbot/tasks/main.yml_b`,

6. **`logs/ansible.log` растёт бесконечно** (`log_path` в ansible.cfg, `/logs/*` в
