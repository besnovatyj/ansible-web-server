# Рекомендуемая итоговая архитектура

## root

Назначение:

* emergency access
* recovery
* single-user mode
* console access

Настройки:

```text
PermitRootLogin no
PasswordAuthentication no
```

При этом:

* root key существует
* ключ с passphrase
* используется только через console/IPMI/provider console/recovery

---

# automation user (ansible)

Например:

```text
ansible
```

Настройки:

* SSH only
* ключи
* желательно passphrase
* sudo NOPASSWD
* password login disabled

---

# human admin user

Например:

```text
alex
ops
admin_alex
```

Настройки:

* SSH only
* ключ с passphrase
* sudo (NOPASSWD или passworded sudo — зависит от модели)
* password auth в SSH отключён

---

# Теперь главный вопрос

> Нужен ли UNIX password у human user?

Короткий ответ:

```text
Да, пароль у пользователя обычно лучше иметь.
Но SSH password authentication должен быть отключён.
```

Это две разные вещи, которые часто путают.

---

# Очень важное разделение

## UNIX password user

Это:

```text
/etc/shadow
```

Пароль локального пользователя.

---

## SSH password authentication

Это:

```text
PasswordAuthentication
```

в sshd_config.

---

# Ключевой момент

Даже если у пользователя есть пароль:

```text
SSH brute force невозможен
```

если:

```text
PasswordAuthentication no
```

---

# То есть вот так — нормально

## Пользователь имеет пароль

```bash
passwd alex
```

---

## Но SSH password login запрещён

```text
PasswordAuthentication no
KbdInteractiveAuthentication no
ChallengeResponseAuthentication no
```

---

# Тогда SSH работает ТОЛЬКО по ключам

И brute force пароля через SSH невозможен.

---

# Тогда зачем вообще пароль?

Вот тут начинается operational reality.

---

# Почему пароль у human user полезен

---

# 1. Local console access

Например:

* hypervisor console
* provider web console
* single-user mode
* rescue shell

---

# 2. sudo with password

Если захочешь:

```text
sudo требует пароль
```

---

# 3. Recovery scenarios

Например:

* SSH сломался
* authorized_keys испорчен
* agent умер
* PAM проблемы

---

# 4. Physical access

---

# Когда можно password lock (`!`)

Для automation users — почти всегда.

Например:

```yaml
password: "!"
```

Это идеально для:

* ansible
* CI users
* deploy users
* service users

---

# Для human users — спорно

Обычно НЕ рекомендуют.

Потому что можно случайно отрезать recovery path.

---

# Лучшая практика

## Для human users

### Иметь пароль

НО:

```text
PasswordAuthentication no
```

---

# Тогда получается:

| Что           | Работает |
| ------------- | -------- |
| SSH по паролю | ❌        |
| SSH по ключу  | ✅        |
| sudo          | ✅        |
| console login | ✅        |
| recovery      | ✅        |

Это лучший баланс.

# А sudo NOPASSWD для человека — стоит ли?

Вот тут уже тонкий момент.

---

# Вариант 1 — sudo NOPASSWD

## Плюсы

* удобно
* быстро
* меньше friction
* хорошо для homelab/small infra

## Минусы

Если украден:

* unlocked SSH session
* ssh-agent
* laptop

→ мгновенный root.

---

# Вариант 2 — sudo С паролем

## Плюсы

Дополнительный security boundary.

Даже если:

* SSH key compromised
* session hijacked

нужен ещё password.

---

## Минусы

* менее удобно
* раздражает
* хуже automation руками

---

# Что обычно делают

---

# Production enterprise

## Human users

```text
sudo требует пароль
```

---

## Automation users

```text
NOPASSWD
```

---

# Small infra / homelab

Часто:

```text
NOPASSWD для всех trusted admins
```

И это нормально.

---

# Очень важный нюанс

Если у человека:

```text
SSH key + passphrase
```

и:

```text
sudo NOPASSWD
```

это всё ещё довольно безопасно.

Потому что атакующему нужно:

1. получить приватный ключ
2. знать passphrase
   ИЛИ украсть unlocked agent/session

---

# Ещё лучше — hardware keys

Например:

* YubiKey
* FIDO2 resident keys
* PKCS11
* smartcard

Тогда даже украсть файл ключа недостаточно.

# Моя практическая рекомендация

---

# Для automation user

```text
password: !
SSH key only
sudo NOPASSWD
```

Идеально.

---

# Для human admin

## Лучший баланс

```text
SSH key + passphrase
local UNIX password exists
PasswordAuthentication no
sudo WITH password
```

---

# Для homelab/small trusted infra

Можно:

```text
sudo NOPASSWD
```

И это не “неправильно”.

---

# Что точно НЕ стоит делать

---

# 1. PasswordAuthentication yes

Если не нужен.

---

# 2. PermitRootLogin yes

---

# 3. Shared accounts

Типа:

```text
admin
root
ops
```

на всех.

---

# 4. Один SSH ключ на всех

---

# 5. Unencrypted private keys

Без passphrase.

---

# Очень хорошая финальная схема

```text
root:
    SSH disabled
    password disabled
    emergency only

ansible:
    SSH key only
    password locked
    sudo NOPASSWD

human:
    SSH key only
    password exists
    sudo requires password
```

Это уже очень зрелая production-модель.
